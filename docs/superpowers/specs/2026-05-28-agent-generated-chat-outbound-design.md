# Agent-Generated Chat Outbound Design

## Decision

All Coke messages visible in user chat channels must be generated by the
Interaction Agent. Gateway, Bridge, Scheduling, and other domain services may
create structured facts, route messages, enforce idempotency, and record
delivery state, but they must not own final user-facing chat prose.

This replaces the current product-notification exception where Gateway writes a
`product_notifications.payload.text` string and sends that text directly to
`/api/outbound`.

The immediate problem is shared-reminder receiver notifications. A receiver
currently gets fixed Gateway text such as:

```text
李梓豪 shared "思考会" for 2026-05-28 21:00, 60 minutes.
```

That is not an Interaction Agent output and therefore violates the chat-visible
message contract.

## Scope

This design covers chat-channel product notifications that are currently
delivered as direct Gateway outbound pushes:

- `shared_reminder_created`
- `shared_reminder_cancelled`
- `direct_friendship_created`

It also defines the durable ownership rule for future chat-visible product
notifications.

The design does not cover non-chat transactional surfaces:

- registration and verification email
- Stripe or subscription email
- admin UI messages
- HTTP API JSON responses and errors
- internal logs, metrics, or audit records

## Core Principle

The system may use multiple physical stores, but each kind of fact has exactly
one authoritative owner:

- Postgres Gateway tables own product facts, notification ledger state,
  customer identity, friendships, shared reminders, and delivery routes.
- Mongo runtime collections own conversation input/output evidence, runtime
  locks, agent session/history state, and reminder runtime wake-up state.
- Interaction Agent text is derived expression. It is never the source of truth
  for product facts.

The immediate issue is not the existence of Postgres and Mongo. The issue is
that Gateway and the Interaction Agent both currently own final chat prose for
different paths. This design removes Gateway as a chat-prose owner.

## Source Of Truth

### Product Notification Facts

`product_notifications` is the authoritative ledger for product-notification
facts and lifecycle.

For migrated chat notifications, the notification payload must contain an
immutable structured facts snapshot instead of final prose. The snapshot should
include the facts needed for the Interaction Agent to generate the message and
for later turns to recover trusted context. Gateway may build a neutral
generation instruction from these facts when it enqueues the runtime turn, but
that instruction is not the final user-visible chat text and must not be stored
as authoritative notification prose.

Example:

```json
{
  "facts": {
    "kind": "shared_reminder_created",
    "resource_type": "shared_reminder",
    "shared_reminder_id": "sr_...",
    "actor_account_id": "ck_creator",
    "actor_name": "李梓豪",
    "recipient_account_id": "ck_receiver",
    "recipient_name": "olivers",
    "title": "思考会",
    "fire_at": "2026-05-28T13:00:00.000Z",
    "timezone": "Asia/Shanghai",
    "local_date": "2026-05-28",
    "local_time": "21:00",
    "duration_minutes": 60,
    "status": "active"
  },
  "facts_hash": "sha256:..."
}
```

The facts are a notification-time snapshot. Later changes to the underlying
shared reminder do not rewrite the historical notification facts.

### Runtime Output Evidence

Mongo `outputmessages` is the authoritative record of what the Interaction
Agent actually said in chat.

For product notifications, output metadata must include:

- `notification_id`
- `notification_kind`
- `resource_type`
- resource id such as `shared_reminder_id` or `friendship_id`
- `facts_hash`
- an event type identifying the output as product-notification delivery

These metadata fields are correlation and idempotency evidence. They are not a
second product-fact source. If Mongo metadata conflicts with Postgres facts,
Postgres wins.

## Data Flow

The target chat notification flow is:

```text
Gateway domain service
  -> write product_notifications pending_delivery with immutable facts
  -> trigger /bridge/inbound as message_type=product_notification for recipient
  -> bridge writes one async inputmessage with trusted product_notification facts
  -> worker handles that input through the normal Interaction Agent user.turn path
  -> Interaction Agent generates final visible text
  -> Mongo outputmessages stores visible output with notification_id metadata
  -> Bridge/Gateway outbound delivers the output to the chat channel
  -> Gateway marks product_notifications delivered from the outbound success path
```

Product notifications are system-originated chat events, not user-authored
messages, but their final prose must still come from the same user-interaction
LLM runtime that handles normal chat turns. The implementation should therefore
reuse the current bridge inbound, inputmessage acquisition, conversation lock,
`AgentInput(input_type="user.turn")`, visible message writing, and outbound
dispatcher path. Do not introduce a third message source or a separate
product-notification LLM.

Do not create an unrelated second handler that duplicates the worker lock,
replay, runtime, and output behavior. If a future typed event such as
`product_notification.received` is introduced, it must remain an adapter over
the same Interaction Agent turn machinery rather than becoming a parallel
generation path.

## Idempotency

One identifier must run through the full path:

```text
notification_id
```

It must appear in:

- `product_notifications.id`
- the internal system-turn event payload
- Mongo `outputmessages.metadata.notification_id`
- Mongo `outputmessages.metadata.product_notification.notification_id`
- outbound `output_id` / idempotency key
- the Gateway outbound delivery request

Retries must first check whether an output already exists for the
`notification_id` and `facts_hash`. If it exists, the system must not generate
or send a second visible message. It should only reconcile missing delivery
state.

If a retry finds the same `notification_id` with a different `facts_hash`, the
event must fail closed as a data-integrity error. It must not pick one version
silently.

## Delivery State

Gateway remains the owner of `product_notifications.status`. Worker and Agent
runtime must not write Postgres directly.

Delivery state should be updated by the layer that observes final outbound
delivery success. In the current topology that layer is the Gateway
`/api/outbound` route, because the bridge dispatcher posts final Mongo
`outputmessages` there and Gateway owns both `outbound_deliveries` and
`product_notifications`.

Required outbound/callback facts:

- `notification_id`
- output message reference
- business conversation key
- delivered timestamp
- optional outbound provider response metadata

The update must be idempotent. Repeating it for an already-delivered
notification is a no-op if the identifiers match. A duplicate-success response
from outbound idempotency must also reconcile the notification as delivered.

If Interaction Agent generation succeeds but the delivered callback fails, the
system must retry reconciliation without regenerating a second message. The
existing Mongo output for `notification_id` is the evidence to reuse.

## User Context Consistency

When a user replies after receiving a product notification, trusted runtime
context must come from Postgres notification facts, not from the previous LLM
text.

The previous LLM text remains normal conversation history. It may help tone and
continuity, but it cannot be the source of facts such as reminder title, time,
duration, sender, friendship id, or shared reminder id.

Gateway's inbound route should thread recent relevant delivered product
notifications into runtime metadata using structured facts and `facts_hash`.
It must not use final prose as `summary_for_llm` when structured facts are
available. A summary may be derived from facts for model readability, but the
facts remain authoritative.

This avoids both common failures:

- context loss: the next turn can recover the notification from the ledger even
  if the LLM's earlier wording omitted a detail
- duplicate facts: the same product fact is referenced by `notification_id`
  instead of copied as separate competing state

## Prompt Contract

The Interaction Agent needs a trusted event block for product-notification
delivery:

```text
event_contract: system product notification delivery;
deliver the notification using the trusted facts;
do not create, update, cancel, or list domain objects unless the event
explicitly instructs such an action.
```

For shared reminders and friendships, the prompt must require preserving all
critical facts:

- actor name
- recipient context when useful
- title or relationship event
- local date and time
- duration when present
- cancellation state when present

The model may choose natural phrasing and tone. It may not alter or omit facts
needed for the user to understand the notification.

## Failure Handling

- Missing recipient delivery route: mark notification failed in Gateway; do not
  generate a visible output.
- Conversation lock unavailable: leave notification retryable; do not generate
  duplicate output.
- Interaction Agent produces no visible output: mark generation failed or
  retryable according to the existing system-turn failure taxonomy.
- Outbound delivery fails: keep the notification retryable and preserve any
  generated output evidence for reconciliation.
- Delivered callback fails after outbound success: retry callback/reconciliation
  with the same `notification_id`; do not regenerate output.

## Documentation Updates

`docs/ARCHITECTURE.md` must be updated when this design is implemented. The
current statement that product notifications are not user inbound turns remains
correct, but the statement that Gateway sends product notifications directly to
`/api/outbound` as final push text must be retired for migrated chat
notifications.

The replacement architecture should say:

- product notifications are system-originated chat events, not user inbound
  turns
- Gateway owns product-notification facts and lifecycle
- Interaction Agent owns final chat prose
- outbound delivery updates Gateway notification state through an idempotent
  delivery callback

## Non-Goals

- Do not migrate all runtime Mongo state to Postgres in this change.
- Do not migrate Gateway product/platform state to Mongo.
- Do not make Worker or Agent runtime a Postgres writer for product state.
- Do not use final LLM text as a product-fact source.
- Do not preserve Gateway-authored final chat prose for migrated notification
  kinds.
- Do not create a parallel system-event handler that duplicates reminder
  delivery locking and replay behavior.

## Verification Requirements

Implementation must include focused tests before deployment:

- Gateway shared reminder creation stores structured notification facts rather
  than final chat prose.
- System-turn delivery writes exactly one Mongo output for one
  `notification_id` across retries.
- A retry after generated output but before delivered callback reconciles state
  without generating another visible message.
- Gateway inbound context threading uses structured notification facts for a
  user's follow-up reply.
- LLM notification output preserves required facts for shared reminder create,
  shared reminder cancel, and direct friendship create.
- Production or staging smoke verifies receiver-visible text, Mongo output
  metadata, and Postgres delivered state for at least one real shared-reminder
  create path.
