# 2026-05-26 Product Action Context Model For Notification Replies

## What Happened

Eva received a shared-reminder invitation notification and later replied with a
short confirmation. The delivered notification had the expected invitation
context, and the inbound Mongo record preserved trusted
`metadata.product_notification`. However, the agent still answered from stale
conversation context about friend invitations instead of treating the reply as a
response to the latest shared-reminder request.

The immediate runtime bug was fixed separately: when trusted product
notification context exists but `product_notification_input_text` is absent,
the runtime now extracts the latest raw user-turn text from the formatted input
before running the deterministic pre-router.

That hotfix mitigates the observed `确认` failure, but it does not settle the
larger product and architecture question: how should the system model context
for user replies to product-generated actionable notifications?

## Why It Matters

Notification replies are not limited to exact keywords such as `确认` or
`拒绝`. Real users may reply with semantic variants, follow-up questions, or
change requests:

- `yes`
- `好`
- `可以`
- `那我参加`
- `谁发的？`
- `几点？`
- `可以改晚一点吗？`
- `我不太方便`

A keyword-only pre-router has poor generalization. A pure transcript-only LLM
approach is more natural at first glance, but it can bind the reply to stale
conversation history, ignore the authoritative business state, or lose the
notification when chat history is truncated or summarized.

The product goal is that the user experiences one continuous conversation. The
architecture question is whether that single user-visible conversation should
internally be represented as a plain chat transcript, or as a typed
conversation event stream that includes actionable product notifications and
business state.

## Current System Status

- Shared-reminder invitation notifications are generated by gateway and now
  include decision-ready text such as requester, title, scheduled time, and
  duration.
- Product-notification metadata is threaded through the bridge into inbound
  user turns as `metadata.product_notification`.
- Agent runtime has deterministic pre-routing for short replies when trusted
  product-notification context is present.
- The 2026-05-26 hotfix handles formatted input such as
  `（2026年05月26日10时40分 eva发来了文本消息）确认` by extracting the latest user
  utterance before short-reply matching.
- The current approach still relies on a narrow set of deterministic reply
  forms before the domain tool is preloaded.

## Core Design Tension

### User Mental Model

From the user's perspective, there should be one chat context. A product
notification should feel like part of the conversation, not like a separate
system channel. If Coke sends an invitation and the user replies `yes`,
`几点？`, or `那我参加`, Coke should understand the reply in that conversational
flow.

### Runtime Requirement

For execution, a notification reply needs more than plain text history:

- a stable business pointer, such as `request_id`
- the notification kind, such as `shared_reminder_request`
- allowed actions, such as `accept` and `reject`
- current domain state, such as `pending`, `accepted`, `rejected`, or `expired`
- expiry or due-time rules
- ambiguity handling when multiple actionable notifications are open

Plain transcript context can help language understanding, but it is not an
authoritative source for action binding or state validation.

## Current Thinking

The likely direction is not to split the user experience into multiple
contexts. Instead, keep one user-visible conversation while representing it
internally as a typed conversation event stream.

In this model, the invitation is part of chat history, but not merely as plain
assistant text. It is stored and passed as a typed event:

```json
{
  "type": "product_notification",
  "kind": "shared_reminder_request",
  "request_id": "cmplyafqf0001nt1tca10n3e6",
  "title": "一起运动",
  "allowed_actions": ["accept", "reject"],
  "status": "pending",
  "expires_at": "2026-05-26T02:30:00Z"
}
```

The runtime can then maintain a current action focus:

1. The latest actionable, still-relevant notification becomes the default focus.
2. The user's next message is interpreted relative to that focus.
3. A semantic resolver classifies the message as `accept`, `reject`,
   `ask_detail`, `request_change`, `ambiguous`, or `unrelated`.
4. The domain executor validates the current business state before any mutation.
5. If the action is expired, already handled, or ambiguous, the agent returns a
   clarification or failure explanation rather than guessing from old chat
   context.

This preserves the user's single-conversation mental model while avoiding a
plain-transcript-only execution path.

## Candidate Architecture

```text
conversation events
  - ordinary user and assistant messages
  - product_notification events
  - action_result events

PendingActionResolver
  - finds the latest actionable product event for this user and conversation
  - excludes expired or already resolved actions when choosing the default focus
  - detects multiple competing candidates

SemanticActionInterpreter
  - uses the current user utterance plus the focused action event
  - may use recent surrounding conversation only as supporting context
  - outputs a structured intent, not free-form execution

DomainExecutor
  - validates request state from the authoritative domain store
  - executes accept/reject only when the current state allows it
  - returns explicit domain failure for expired or invalid actions

Agent response
  - explains the result or asks a clarification in natural language
```

## Open Questions For Expert Review

- Should "latest actionable notification" always become the default focus, or
  should focus be scoped by channel, conversation, notification kind, or a time
  window?
- What should count as actionable: only product notifications with
  `allowed_actions`, or also reminder fires and other domain events?
- Should the semantic interpreter be deterministic rules first, LLM first, or a
  hybrid classifier with confidence thresholds?
- How should follow-up questions work? For example, if the user asks `几点？`,
  should the action remain focused for a later `可以`?
- How should the system handle multiple pending invitations from different
  people?
- Where should the typed event stream live: Mongo chat history, gateway product
  notification tables, a dedicated action-context table, or a derived runtime
  view across stores?
- What evidence is required before changing the runtime contract: unit tests,
  worker-runtime tests, live smoke, corpus cases, or all of them?

## Non-Goals For This Issue

- Do not add more hard-coded confirmation synonyms as the long-term fix.
- Do not make the LLM freely search the entire historical transcript to decide
  which business object to mutate.
- Do not expose multiple contexts to the user. The product experience should
  remain one conversation.

## Evidence To Preserve

- Eva's shared-reminder notification was delivered at
  `2026-05-26T01:22:32.655Z` with `kind=shared_reminder_request`.
- Eva replied at `2026-05-26T02:40:04Z` with `确认`.
- The inbound user message preserved `metadata.product_notification`.
- The agent run did not call a scheduling tool and answered from stale friend
  invitation context.
- The related shared-reminder request had `fire_at=2026-05-26T02:30:00Z`, so a
  correct routed action should have reached the domain layer and surfaced an
  expired or invalid-state result instead of drifting into another topic.

## Current Status

Open for design review. The observed formatted-confirmation failure has a
